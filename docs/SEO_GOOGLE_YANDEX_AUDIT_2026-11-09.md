## 2. Что уже реализовано корректно по проектному коду

- SSR HTML для значимых страниц, новостей и начальной выборки 44 актов (`force-dynamic`, `searchVerifiedCourtActs("")` на сервере); карточки имеют обычные `Link`, а судебные решения — собственные HTML URL. Клиентский поиск не является единственным способом открыть дело.
- `robots.ts` в открытом режиме отдаёт Allow /, ограничивает /admin/ и /api/, объявляет sitemap; в закрытом режиме отвечает Disallow /. Разделение открытого/закрытого релиза намеренное. Прямые PDF /api дополнительно имеют `X-Robots-Tag: noindex`, а основное содержимое судебных актов доступно в HTML (при правильном deploy).
- Sitemap формируется из разрешённых legacy-страниц, новостей и проверенных судебных актов; не публикует 18 draft-руководств и неподтверждённые CMS-строки.
- Self-canonical metadata для открытых legacy/новостных/судебных маршрутов; единый `https://dgi-pravo.ru`; код постоянного redirect www → apex; 404 через `notFound`. Реальные ответы требуют live-проверки.
- `<html lang="ru">`, заголовки и метаописания, OG/Twitter, `WebPage`/`BreadcrumbList` на опубликованных старых статьях и судебных страницах; не фабрикуются авторы/рейтинги/исходы дел.
- Next/Image используется для логотипа с фиксированным размером. Есть Playwright-проверки мобильной адаптации; их успех не заменяет полевые LCP/INP/CLS.

## 3. Приоритет P0 — до масштабирования индексации

### P0.1. Реальное состояние release/indexability в Coolify — НЕ ПОДТВЕРЖДЕНО

Код `apps/web/src/data/pages.ts` и `apps/web/src/proxy.ts` требует одновременно `SITE_CUTOVER=true`, `SITE_RELEASE_APPROVED=yes`, `SITE_URL=https://dgi-pravo.ru`. Иначе `X-Robots-Tag: noindex`, `robots.txt` запрещает обход, `sitemap.xml` пуст, а судебные HTML-карточки скрыты. Исторический issue #34 (27.10) отмечал `Disallow: /`, 0 sitemap URL и `noindex`; новое развёртывание могло изменить состояние.

**Действие:** только чтение конфигурации Coolify и HTML на production; сверить deployed commit с защищённой базой, 200 заголовки 3–5 основных страниц, index/noindex, robots/sitemap, и одну актуальную новость + HTML акт + PDF. Не менять глобальные флаги автоматически. Новый штатный аудит должен проверять как *открытые утверждённые URL*, так и *закрытые черновики*.

### P0.2. Мониторинг SEO устарел и может давать ложные тревоги — ПОДТВЕРЖДЕНО КОДОМ

`scripts/seo-live-audit.mjs` считает ошибкой **отсутствие `noindex`** (`unreviewed_beta_missing_noindex`), отсутствие `Disallow: /`, и наличие URL в sitemap — это контроль старого закрытого beta-сайта, прямо противоречащий текущей цели открытого публичного SEO. `.github/workflows/seo-live-audit.yml` запускает именно его. В то же время `scripts/check-live-indexability.mjs` проверяет уже правильный открытый режим, а `scripts/weekly_seo_audit.py` тоже предусматривает открытый сайт: **три несовместимых режима проверки**.

**Действие:** выделить `preview` и `published` режимы; production должен валидировать минимум Allow /, sitemap фактически опубликованных URL, HTTP 200, canonical и отсутствие noindex у открытых URL; отдельно гарантировать noindex/404 у 18 черновиков, API и PDF согласно релизной политике. Не использовать один и тот же тест с противоречащими ожиданиями.

### P0.3. GitHub schedule может проверять не ту ветку — ПОДТВЕРЖДЁННАЯ КОНФИГУРАЦИОННАЯ ОПАСНОСТЬ

Default branch репозитория — `main`, а актуальное приложение и релиз — `infra/coolify-russian-vps`. По официальной GitHub Docs `schedule` исполняется только на default branch. Код `main` отличается от protected production: как минимум отсутствуют нынешние каталоги новостей и судебных актов. Даже успешный nightly/weekly run из `main` нельзя считать тестом актуальной release-ветки.

**Действие:** разработать безопасный dispatcher/schedule на default branch с checkout строго конкретного SHA защищённой production-ветки либо контролируемый внешний мониторинг без записывающего доступа; записывать `audited_sha`, `deploy_sha` и время сканирования в каждый артефакт. Запуски на PR проверяют PR, а не настоящий HTTP production.

## 4. Приоритет P1 — адресные недоработки

### P1.1. Разметка WebSite не появляется на домашнем маршруте — ПОДТВЕРЖДЕНО КОДОМ

`SeoMarkup.tsx` создаёт JSON-LD `WebSite`, но вызывается только из `MigratedArticle`. Текущая `apps/web/src/app/page.tsx` не рендерит `MigratedArticle` и `SeoMarkup`, а самостоятельно строит главную. Поэтому главный URL не выводит эту разметку через указанный компонент. Google рекомендует `WebSite` с `name,url` именно на **главной** для названия сайта; `og:site_name` тоже учитывается.

**Действие:** добавить один достоверный `WebSite` JSON-LD на / при indexable release; согласовать фактическое (не вводящее в заблуждение) название с header, title, OG и About. Не создавать дублирующую разметку/не выдумывать официальную аффилиацию.

### P1.2. Несогласованные названия сайта — ПОДТВЕРЖДЕНО КОДОМ

`layout.tsx` и `PageShell.tsx` используют длинное «Единая справочная служба Москвы», шапка — «Жилищный справочник Москвы», `SeoMarkup` — «Единая справочная служба Москвы». Риск: неочевидный бренд и возможное впечатление официальной городской структуры при независимом характере проекта.

**Действие:** выбрать проверяемое единое наименование без намёка на государственные полномочия; одинаково использовать в title, WebSite, og:site_name, шапке и footer. Наличие правовых отказов/дисклеймеров сохранять.

### P1.3. Нарушенный якорь из публичного материала — ПОДТВЕРЖДЕНО КОДОМ

В `pages-*.json` есть ссылка из `/pereraschet-zhku-moskva` на `/#practical-housing-guides`. `legacy-anchors.json` содержит этот идентификатор для исторической главной Webflow, но новая `app/page.tsx` использует `id="topics"`, а `practical-housing-guides` не выводит. Восьмерка других исходных ссылок с фрагментами лежит в legacy-блоках домашнего контента, но эта часть старой главной не рендерится новой `app/page.tsx`; не объявлять эти 8 ссылок текущими live-ошибками.

**Действие:** заменить точечную ссылку на `/#topics` (после UI-проверки назначения); расширить тест фрагментов и ссылок на реально рендеримые страницы.

### P1.4. Нет достоверного поля обновления для новостей и статических судебных актов

`sitemap.ts`: у новостей `lastModified = publishedAt`, то есть дата выпуска статьи, даже если содержимое позднее исправлялось. У 44 статических судебных HTML URL `lastModified` отсутствует, что допустимо. Google использует `lastmod` только если он **проверяемо точный**; `priority` и `changefreq` игнорирует.

**Действие:** ввести проверяемое `contentUpdatedAt` при реальном существенном изменении статьи; не подменять датой сборки/деплоя/проверки. Не генерировать фиктивный lastmod для судебных актов или устаревших правовых страниц. Параметры priority/changefreq можно оставить ради совместимости, но не считать преимуществом для Google.

### P1.5. Тонкие навигационные статьи — НЕ АВТОМАТИЧЕСКОЕ SEO-НАРУШЕНИЕ

`/zhilishchnaya-ochered` (40 слов p-блоков), `/kadastrovaya-stoimost` (48), `/zhilishchnye-subsidii` (51), также `/dokumenty-na-kvartiru` (70). Установить, отвечает ли каждая потребности пользователя, не ведёт ли к ошибочному впечатлению о праве на услугу. Google НЕ задаёт оптимального объёма в словах; SEO-рерайт без новых достоверных фактов ухудшит качество.

**Действие:** добавить оригинальные юридически сверенные сценарии и калькуляторы/документные формы только там, где обоснованы, с источниками, датой сверки и исключениями. Не публиковать исследовательские черновики ради количества URL.

### P1.6. Структурированные данные и сниппеты новых материалов

Есть `WebPage`/`CreativeWork`/`BreadcrumbList` у судебных HTML актов и OG Article у новостей, но детальная новость не содержит собственного JSON-LD `Article`/`NewsArticle` с подтверждаемыми полями. Это **улучшение, не обязательная ошибка**. Яндекс анализирует Schema.org, title, description; Google требует, чтобы свойства разметки соответствовали видимому контенту.

**Действие:** добавить BreadcrumbList для новости, а `NewsArticle` только если есть реальные заголовок, дата, источник, publisher и необходимые свойства; без выдуманного автора, картинки, лицензии и рейтингов. Проверять через Schema Markup Validator и Google Rich Results Test для поддерживаемых типов (результат в выдаче не гарантирован).

### P1.7. Мониторинг Core Web Vitals и скорости — НЕ ИЗМЕРЕН

`.github/workflows/seo-lighthouse-audit.yml` существует, но не настроен как регулярный тест production после каждого release; выбирает лишь четыре маршрута по mobile/desktop и запускается вручную или при push в старую `seo/official-google-yandex-audit-20261018`. `layout.tsx` загружает Яндекс Метрику с Webvisor; реальный вклад в LCP/INP/CLS неизвестен. Оценивать синтетически и полевыми данными раздельно.

**Действие:** лабораторные прогонные и smoke-тесты для /, новых статей, судебных страниц, длинных руководств, форм, mobile. Проверить кеширование, JS, TTFB, стили, CLS, адаптивность и влияние сторонних скриптов. Целевые p75 CWV: LCP ≤2,5 c, INP ≤200 мс, CLS ≤0,1 — не выдавать за измеренные текущие значения.

### P1.8. Поисковые консоли, регион и обратная связь — ДАННЫХ НЕТ

Есть файл подтверждения Яндекс Вебмастера и скрипт Google DNS check; **не доказано**, что обе консоли подтвердили собственность, видят sitemap, содержат статистику либо что задан регион для Яндекса.

**Действие:** прочитать реальные отчёты Google Search Console (Page indexing, URL Inspection, Search performance, CWV) и Яндекс Вебмастера (Страницы в поиске, Диагностика, sitemap, регион, запросы, исключённые URL). Без этих данных невозможно честно оценить CTR, позиции и долю проиндексированных страниц. После подтверждения можно подключить IndexNow для новых/обновлённых/удалённых **опубликованных** URL, с проверкой ownership key.

## 5. Приоритет P2 — улучшения без фиктивных SEO обещаний

- Спроектировать внутренние тематические кластеры с фактической рубрикацией и ссылками между справкой, документом, новостью и судебным актом (по одной теме, но без неоснованных юридических выводов). Не ссылаться на черновики с indexable страниц.
- Для судебной практики объяснять, почему конкретный акт релевантен теме, но не утверждать итоговый выигрыш или прецедентность без текста. Возможна тематическая навигация и разрешённые серверные страницы пагинации при росте архива; `/api` и пользовательские результаты поиска не индексировать.
- Проверить старые Webflow URL и фактическую карту 301 при миграции, не массово перенаправлять всю структуру на главную. Статический анализ исходных 33 страниц не нашёл ссылок на webflow.io, но внешние обратные ссылки и поведение старого домена не обследованы.
- Сократить повторяющиеся предупреждения на фронтенде без потери важных юридических ограничений. Добавлять изображения/схемы только при ясной пользовательской пользе и установленных правах; бесполезная графика не оптимизация.
- Не использовать неофициальные «AEO/GEO трюки», `llms.txt` как обязательный сигнал Google, фальшивые квалификации, отзывы, авторов, индексацию CMS-черновиков, накрутку метрик, автоматическую замену устаревшего закона заведомо неточным.

**Этап 2 (P1):** один правдивый WebSite на /, согласование бренда, устранение неверного якоря, структурированные данные и дата обновления только с подтверждением. Регрессионные тесты 33 migrated + 26 news + 44 court URLs, без публикации 18 drafts.

**Этап 3:** Google Search Console / Яндекс Вебмастер — проверка доступности sitemap и выборки URL, статус «проиндексировано / исключено», реальные показы/клики/CTR, Яндекс регион, полевые CWV. Без доступа к этим данным этап не может считаться завершённым.

**Этап 4:** юридически верифицировать и расширять по ценности отдельные слабые темы, перелинковку и инструменты; защитить текущие 44 суда от несанкционированного раскрытия персональных сведений, не переносить PDF API в sitemap. Плановое обновление норм без фальшивых дат.

**Правила:** исправления в отдельной `automation/dgi-*` ветке через PR в `infra/coolify-russian-vps`, CI по final SHA, не обходить ruleset, не изменять production secrets/robots/site flags без доказательств, не запускать VPS/Coolify Deploy, не обещать индексацию/позиции без реальных данных.
