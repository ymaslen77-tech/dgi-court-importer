# ДГИ — стандарт разработки, размещения и эксплуатации сайта

**Статус документа:** утверждённая целевая архитектура и правила жизненного цикла проекта.  
**Зафиксировано:** 15 октября 2026 года.  
**Текущий режим:** доработка в GitHub без развёртывания на Vercel и без изменения действующего сайта.

> **Разграничение статусов:** архитектура ниже задаёт, **как должен работать проект после ввода в эксплуатацию**, а не доказывает, что каждый внешний сервис уже подключён. Запись стандарта в репозитории не означает разрешение на публикацию. Для ДГИ по-прежнему требуется отдельная юридическая, редакционная, эксплуатационная и SEO-приёмка.

## 1. Полная схема разработки, размещения и работы

| № | Компонент | Функция и ответственность | Статус / граница |
|---|---|---|---|
| 1 | **Локальная разработка** | Создание сайта, программирование, проверка UI и API, локальные тесты, изолированная БД. | Разработка и локальные сценарии предусмотрены в репозитории. |
| 2 | **GitHub — репозиторий** | Единый источник исходного кода, ветки, история изменений, Pull Requests, ревью и документация. | Используется: `ymaslen77-tech/dgi-court-importer`. |
| 3 | **GitHub Actions — CI/CD** | Сборка, статический анализ, тесты Next.js, CMS и PostgreSQL, проверка качества, контролируемая подготовка миграций. | CI реализован. Выполнение workflow **не равно** разрешению применять миграции к production и публиковать сайт. |
| 4 | **Vercel — основной хостинг** | Целевой runtime Next.js, SSR, API Routes, HTTPS, Preview и Production Deployment. | Целевая схема публикации; **не разворачивать из текущей офлайн-ветки**. |
| 5 | **Neon — PostgreSQL** | Основная целевая БД: таблицы, пользователи, данные, транзакции, изолированные ветки/окружения, управляемое подключение. | **Проект Neon `dgi-court-importer` создан 16.10.2026.** PostgreSQL 17; `main` и `staging`; базы `dgi`, `dgi_cms`. В `dgi` применены миграции 0001–0005 и импортированы 33 страницы, 16 кандидатов судебных дел и 50 записей CMS (все закрыты для публикации). Runtime Payload и подключение к Vercel ещё не выполнены. [Подробная проверка](NEON_DGI_BOOTSTRAP_2026-10-16.md). |
| 6 | **Домен + DNS** | Собственный адрес, маршрутизация на хостинг, управление DNS, корректный HTTPS. | Действующий домен и DNS **не переключать** до отдельного решения о выпуске. |
| 7 | **Пользователи сайта** | Открывают страницы, входят в учётные записи при наличии соответствующих функций, используют разрешённые сервисы. | Доступность функций зависит от реальной реализации и редакционного допуска материалов. |

**Логическая схема доставки приложения:**

```text
Локальная разработка
        ↓
GitHub (ветка → Pull Request → review)
        ↓
GitHub Actions (CI, тесты и контроли)
        ↓ [только после допуска к выпуску]
Vercel (Preview / Production, Next.js) ↔ Neon (PostgreSQL)
```

**Схема пользовательского запроса после запуска:**

```text
Пользователь → Домен / DNS → Vercel (HTTPS)
            → Next.js: SSR / API / авторизация
            → Neon: запросы / транзакции / данные
            → Ответ пользователю
```

В рабочем приложении браузер **не подключается к Neon напрямую по секретному соединению**: доступ к данным идёт через разрешённую серверную логику или отдельно спроектированный безопасный слой авторизации.

## 2. Дополнительные компоненты инфраструктуры

| Компонент | Назначение | Целевое размещение / решение |
|---|---|---|
| **Фоновые задачи** | Длительные процессы, очереди, импорт, обработка файлов. | Отдельный worker и очередь; возможность конкретного механизма Neon Functions требует оценки и подтверждения, **не считается действующей по умолчанию**. Не запускать долгие очереди внутри обычного HTTP-запроса Vercel. |
| **Планировщик** | Регулярные задания и обновления данных. | Vercel Cron для предусмотренных периодических вызовов либо отдельный планировщик; Neon — только если выбранная функция/интеграция действительно поддерживает требуемое расписание. |
| **Файловое хранилище** | PDF, изображения, сканы, вложения. | Отдельное S3-совместимое объектное хранилище с контролем доступа, прав на медиа и жизненным циклом файлов; не PostgreSQL и не временный диск функции как постоянное хранилище. |
| **Авторизация** | Регистрация, вход, сессии, роли, разграничение доступа. | Приложение / отдельно проверенный Neon Auth; в проекте уже предусмотрены защищённые роли Payload CMS, но это **не подтверждает наличие публичной пользовательской регистрации или подключение Neon Auth**. |
| **Мониторинг** | Логи, ошибки, доступность, производительность, оповещения. | Vercel и/или внешняя система мониторинга; фиксируются ответственные, пороги и каналы уведомления. |
| **Резервное копирование** | Восстановление БД и критических данных. | Возможности восстановления Neon **плюс независимые зашифрованные резервные копии**, проверка восстановления, отдельное резервирование объектов. |
| **Защита** | HTTPS, секреты, RBAC, защита API и БД, ограничение публикации. | Vercel / Next.js / Payload / Neon / внешние средства; секреты только в защищённых настройках окружения, не в Git. |

**Условия выбора необязательных компонентов:** worker, очередь, планировщик, файловое хранилище, аутентификация и мониторинг должны иметь утверждённого поставщика, настройки безопасности, тестовый сценарий и операционную инструкцию до появления отметки «внедрено». Указанные здесь варианты не означают, что сервисы уже созданы.

## 3. Окружения и данные

| Среда | Код | База данных | Индексация и публикация |
|---|---|---|---|
| **Development** | Локальная ветка разработчика | Локальная PostgreSQL / одноразовые тестовые БД, раздельно сайт и CMS | Нет публичного выпуска; тестовые данные. |
| **CI / Pull Request** | SHA коммита в GitHub Actions | Эфемерная PostgreSQL и CMS-среда | Только тестирование; production-секреты не выдаются. |
| **Preview** *(цель)* | Изолированная сборка PR на Vercel | Отдельная Neon staging/preview branch, без доступа к production-данным по умолчанию | `noindex`, контроль доступа, никакой публикации неподтверждённого контента. |
| **Staging** *(цель)* | Кандидат на выпуск | Изолированная Neon staging branch/БД; отдельные учётные данные и схема миграций | Интеграционные, E2E, безопасность, юридическая и SEO-проверка. |
| **Production** *(цель)* | Утверждённая версия из `main` | Production Neon branch/БД с минимально необходимыми правами | Только одобренные материалы; домен и индексация — после отдельного разрешения. |

Для разделённых БД сайта и Payload CMS сохранять раздельные `DATABASE_URL` и `CMS_DATABASE_URL`, схемы, роли, миграции и резервное восстановление. Neon branching **не заменяет** проверку миграций или независимое резервное копирование. Данные production нельзя автоматически переносить в Preview без проверки приватности и правил обезличивания.

## 4. Стандарт работы и публикации

1. **Development.** Реализация и локальная проверка интерфейса, TypeScript, API, SQL и CMS без изменений production.
2. **GitHub Branch.** Коммиты в отдельной ветке; рабочий `main` остаётся стабильным.
3. **Pull Request.** Code review, GitHub Actions, регрессионные и интеграционные тесты, проверка секретов, юридических/редакционных ограничений.
4. **Preview Deployment.** В обычном режиме Vercel создаёт отдельную защищённую ознакомительную сборку PR. **В текущем режиме офлайн-доработки этот этап пропускается; отсутствие Preview не блокирует сохранение и CI-контроль кода.**
5. **Staging Database.** Для будущего полного процесса создать отдельную ветку/БД Neon, изолировать права и данные, проверить подключение приложения и CMS.
6. **Merge в `main`.** Только при зелёном CI, ревью и утверждённом решении о слиянии. Автоматические тесты **сами по себе не разрешают merge или юридическую публикацию**.
7. **Production Deployment.** В целевой конфигурации Vercel автоматически публикует разрешённый merge/tag; включать автоматическое развёртывание **только после** готовности хостинга, БД, секретов и формальной приёмки. До этого автодеплой должен быть отключён/ограничен.
8. **Database Migrations.** Сначала dry-run и проверка миграций на staging; затем контролируемый production-проход с проверкой совместимости, снимками/backup и планом восстановления. Порядок deploy ↔ DB migration зависит от типа изменений; для несовместимых изменений использовать expand/migrate/contract.
9. **Monitoring.** Проверка здоровья приложения, логов, ошибок, производительности, БД, очередей, сертификатов и уведомлений после изменений.
10. **Rollback.** Возврат к предыдущему рабочему развёртыванию по утверждённой процедуре; **откат приложения не откатывает БД автоматически**. Для данных и схем применяют отдельно спланированное обратимое изменение либо восстановление из проверенных бэкапов с учётом риска потери новых транзакций.

### Политика миграций и выпуска

- Тестовая CI-БД одноразовая. В GitHub Actions запрещено автоматически направлять тестовые миграции на рабочую Neon-БД.
- Для production-миграций требуется отдельный защищённый workflow/ручное подтверждение с контролем среды и прав, даже после merge.
- Полные SQL-дампы, секреты, персональные данные пользователей и закрытое исходное содержимое CMS не коммитятся в Git.
- `SITE_CUTOVER`, `SITE_RELEASE_APPROVED`, `CMS_PUBLIC_READS` и `COURT_DB_READS` по умолчанию остаются выключенными. Редакционно неподтверждённые материалы не становятся опубликованными от переключения глобальных флагов.
- Судебные акты, нормы, редакции регламентов, медиа и права на использование материалов допускаются только после их самостоятельной проверки; состояние «CI Passed» не является юридической приёмкой.

## 5. Распределение ответственности

| Система | За что отвечает | За что **не** отвечает |
|---|---|---|
| **GitHub** | Исходный код, PR, версии, история, ревью и документация. | Не является исполняющим хостингом пользовательского сайта. |
| **GitHub Actions** | Контроль качества, тесты и разрешённые автоматизации. | Не даёт права публиковать непроверенные юридические материалы. |
| **Vercel** | Сборка, публикация, HTTPS и выполнение Next.js/SSR/API. | Не является основной PostgreSQL-БД или долговременным хранилищем файлов. |
| **Neon** | PostgreSQL-данные, ветки БД, транзакции и управляемые подключения. | Не заменяет весь веб-хостинг, DNS и полнофункциональный файловый архив. |
| **Домен/DNS** | Публичный адрес и направление трафика на выбранный хостинг. | Не хранят код, профили и судебные материалы. |
| **Команда / владелец проекта** | Законность содержания, допуск к релизу, контроль секретов, резервное восстановление, мониторинг. | Не должны считать автоматическую зелёную проверку подтверждением юридических источников. |

## 6. Текущий режим работ по ДГИ (не путать с целевой архитектурой)

**Ветка:** `feature/dgi-offline-completion`; **production и `main` не изменять**. Конфигурации `vercel.json` и `apps/web/vercel.json` содержат `git.deploymentEnabled["feature/dgi-offline-completion"]=false`. Без развёртывания, переключения DNS и изменения работающего сайта допускаются:

- изменения frontend, юридических инструкций, структуры CMS, каталогов и документов;
- проверка Next.js, Payload и PostgreSQL в GitHub Actions;
- офлайн-сборки и проверки защиты публикации;
- документирование результатов, блокеров и готовности к будущему выпуску.

**Подтверждено конфигурацией репозитория:** Next.js-приложение `apps/web`, Payload `apps/cms`, PostgreSQL 17 в Docker Compose/CI, GitHub Actions, режим `noindex` и ограничения редакционной публикации. **Не подтверждено:** наличие действующего подключённого проекта Neon, production Neon branch, защищённого постоянного Vercel staging, готовых worker/S3/Neon Auth, завершённой операционной приёмки и разрешённого перехода на новое приложение.

Для фиксации фактических проверок и юридических ограничений см. [офлайн-отчёт](OFFLINE_COMPLETION_QA_2026-10-14.md), [критерии выпуска](RELEASE_READINESS.md) и [инструкцию по изолированному staging](STAGING_RUNBOOK.md).

**Итоговый норматив архитектуры:**  
`Разработка → GitHub → GitHub Actions → Vercel ↔ Neon`  
`Пользователь → Домен/DNS → Vercel → Серверная логика → Neon`

Это **целевая промышленная схема**, а не сообщение об уже состоявшемся развёртывании. До снятия ограничений действующего проекта применяется только `Разработка → GitHub → GitHub Actions`.
