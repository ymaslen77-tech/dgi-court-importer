# Полная схема разработки, размещения и работы сайта ДГИ

**Версия документа:** 1.0 · **Дата:** 15.10.2026  
**Статус:** утверждённая целевая архитектура; не свидетельствует о фактическом подключении всех сервисов или разрешении публикации.

> **Принцип:** GitHub хранит код; GitHub Actions контролирует качество; Vercel предназначен для запуска веб-приложения; Neon — для PostgreSQL; домен/DNS направляет пользователей на хостинг. Пока завершается офлайн-разработка, никакой production deployment, переключения DNS и изменений действующего сайта нет.

## 1. Основная архитектура

| № | Компонент | Назначение | Где расположен / роль |
|---|---|---|---|
| 1 | **Локальная разработка** | Создание сайта, программирование, ручное и автоматизированное тестирование | Компьютер разработчика; локальные Next.js, Payload CMS и тестовая PostgreSQL |
| 2 | **GitHub — репозиторий** | Исходный код, ветки, история изменений, code review и Pull Requests | `ymaslen77-tech/dgi-court-importer` |
| 3 | **GitHub Actions — CI/CD** | Проверки кода, типизации, безопасности, сборки, E2E, CMS/БД; контролируемая подготовка выпуска | GitHub-hosted runners; миграции — отдельным разрешённым процессом |
| 4 | **Vercel — основной целевой хостинг** | Сборка/размещение Next.js, SSR, Route Handlers / API Routes, HTTPS и Preview | Веб-приложение, а не основная PostgreSQL |
| 5 | **Neon** | Основная PostgreSQL: таблицы, пользователи приложения, контент, транзакции, отдельные ветки БД для сред | Управляемая PostgreSQL, соединение через серверную часть |
| 6 | **Домен + DNS** | Публичный адрес сайта, DNS-записи, подтверждение домена, HTTPS | DNS-провайдер + Vercel, когда публикация отдельно согласована |
| 7 | **Пользователи** | Просмотр материалов, авторизация (если предусмотрена функцией), взаимодействие с сервисами | Браузер → домен → Vercel → серверная логика → PostgreSQL |

**Цепочка разработки:**

```text
Локальная разработка → GitHub (ветка / PR) → GitHub Actions (проверки)
                                           ↓ только после отдельного допуска
                                     Vercel (Next.js) ↔ Neon (PostgreSQL)
```

**Цепочка пользовательского запроса после запуска:**

```text
Пользователь → Домен / DNS → Vercel → Next.js SSR / API → Neon PostgreSQL
                                              ↘ разрешённые внешние сервисы / файловое хранилище
```

Браузер не подключается непосредственно к PostgreSQL. Секреты соединения используются только серверной логикой; чувствительные данные не включаются в `NEXT_PUBLIC_*`.

## 2. Дополнительные компоненты инфраструктуры

| Компонент | Назначение | Целевое размещение / замечания |
|---|---|---|
| **Фоновые задачи** | Долгие операции, обработка очередей, тяжёлый импорт судебных данных, генерация файлов | Отдельный worker с очередью и контролем повторов; функции платформы Neon — только при отдельно подтверждённой поддержке требуемого сценария |
| **Планировщик** | Регулярные обновления, синхронизация и контроль заданий | Vercel Cron для коротких запусков либо внешний планировщик для worker; GitHub Actions schedules допустимы для репозиторных задач |
| **Файловое хранилище** | PDF, изображения, приложения и исходные документы | S3-совместимое объектное хранилище с приватным доступом, политиками хранения и правами на медиа |
| **Авторизация** | Регистрация/вход, сессии, роли, контроль доступа | Приложение и/или Neon Auth после отдельного решения; существующие роли редакции реализованы в Payload CMS, их нельзя считать Neon Auth |
| **Мониторинг** | Доступность, ошибки, логи, производительность, уведомления | Vercel + внешняя система для ошибок/метрик, логи worker и БД |
| **Резервное копирование** | Восстановление БД и файлов, проверка резервных копий | Возможности восстановления Neon **плюс независимые зашифрованные резервные копии** БД и файлов; регулярный тест восстановления |
| **Защита** | HTTPS, хранение секретов, разграничение ролей, защита API, rate limiting и аудит | Vercel + приложение + Neon; принцип минимальных прав, разные credentials для сред |

**Ограничения размещения:** Vercel предназначен прежде всего для веб-запросов и ограниченных по времени функций, а не для постоянно работающих длинных обработчиков. Neon обеспечивает БД, но сам по себе не заменяет очередь, worker, файловое хранилище или полноценную стратегию резервного копирования. Наличие названного сервиса в таблице не означает, что интеграция уже настроена.

## 3. Разделение сред

| Среда | Код | База | Публикация |
|---|---|---|---|
| **Development** | Локальная рабочая копия | Локальная PostgreSQL / одноразовая БД | Не публикуется |
| **CI** | Коммит / PR | Одноразовая PostgreSQL GitHub Actions | Не публикуется |
| **Preview** | Ветка / Pull Request | Изолированная тестовая ветка Neon либо отдельная тестовая БД, когда будет настроено | Защищённый Vercel Preview **только если развёртывания отдельно разрешены** |
| **Staging** | Проверенная кандидатная версия | Выделенная staging-ветка Neon, раздельные права и данные | Закрытая тестовая среда; никакого production DNS |
| **Production** | Одобренный выпуск из `main` | Production PostgreSQL в Neon | Основной домен, HTTPS, мониторинг |

Для данного проекта **веб-БД и БД Payload CMS — логически и по учётным данным раздельные**. Не направлять обе схемы в одну неподготовленную базу. Тестовые записи, копии персональных данных и непроверенные CMS-материалы не должны автоматически попадать в production. Ветки Neon для Preview создаются и удаляются только после отдельной настройки жизненного цикла, а не «сами собой» от любого PR.

## 4. Стандарт работы и публикации — 10 этапов

1. **Development:** разработка и тестирование локально; не использовать боевую БД для опытов.
2. **GitHub Branch:** каждое изменение в отдельной ветке; небольшие и проверяемые коммиты.
3. **Pull Request:** code review, статические проверки, тесты Next.js, Payload CMS, PostgreSQL, безопасность и браузерные E2E через GitHub Actions; ошибки блокируют объединение.
4. **Preview Deployment:** после разрешения Git-интеграции Vercel создаёт защищённую предварительную версию; в текущем офлайн-режиме **этап намеренно пропускается**.
5. **Staging Database:** отдельная Neon branch/БД с тестовыми данными; проверка миграций и взаимодействия сайта/CMS; пока Neon не подключён — только изолированная локальная или CI PostgreSQL.
6. **Merge в `main`:** только после зелёного CI, разрешённого review, юридической/контентной приёмки и подтверждения безопасности; в текущем этапе **запрещён**.
7. **Production Deployment:** отдельный разрешённый выпуск через Vercel после снятия организационных и технических блокировок; никакой автоматической публикации черновиков.
8. **Database Migrations:** версионированные, заранее протестированные изменения схемы, с отдельными полномочиями, планом совместимости (expand/contract), резервной копией/точкой восстановления и процедурой отката; **не запускать опасные миграции автоматически при сборке или на каждом Preview**. Фактический порядок «миграция ↔ приложение» определяется обратной совместимостью конкретного изменения.
9. **Monitoring:** после запуска проверять health checks, логи, ошибки, показатели производительности, соединения с PostgreSQL и уведомления.
10. **Rollback:** возвращать предыдущую совместимую версию развёртывания; восстановление БД выполнять по отдельному плану с учётом уже выполненных транзакций и изменений схемы. Откат Vercel **не отменяет** миграции БД автоматически.

**Важная граница:** успешно прошедший CI не разрешает выпуск неподтверждённых судебных решений, нормативных актов и редакционных черновиков. Отдельно требуются юридическая, редакционная, визуальная, SEO и эксплуатационная приёмка.

## 5. Распределение ответственности

| Система | Ответственность |
|---|---|
| **GitHub** | Единый источник исходного кода и управление разработкой |
| **GitHub Actions** | CI, автоматические проверки, контролируемые задачи и правила выпуска |
| **Vercel** | Основной целевой хостинг, сборка, публикация и выполнение веб-приложения |
| **Neon** | Основная целевая PostgreSQL и изолированные ветки/среды БД |
| **Домен/DNS** | Публичный адрес и направление трафика |
| **Next.js / Payload CMS** | Пользовательские страницы, API, серверная логика; редакционные процедуры и роли |
| **Оператор проекта** | Доступы, секреты, стоимость сервисов, подтверждение миграций, юридический допуск и разрешение на выпуск |

| **GitHub Actions** | Настроены CI и Playwright; есть отдельный тест запрета публикации неподтверждённых материалов | Все checks на выпускном коммите и ручная приёмка |
| **Next.js** | Код сайта в `apps/web`; проверяется в CI | Закрыть оставшиеся юридические, дизайн-, SEO- и эксплуатационные ограничения |
| **Payload CMS** | Код в `apps/cms`, редакционные роли/ворота и изолированная тестовая PostgreSQL | Подтвердить постоянное безопасное окружение, импорт и восстановления |
| **Neon** | **Целевой сервис; подключение production/staging к данному проекту здесь не подтверждено** | Создать/проверить проект, разделение БД, credentials, миграции, резервные копии |
| **Vercel** | Предусмотрен для релиза; в офлайн-ветке авторазвёртывание отключено конфигурацией; существующая Preview-ссылка не является выпуском | Ничего не развёртывать до отдельного разрешения |
| **Домен/DNS** | Переключение для новой версии не выполнено и не разрешено | После подписанной приёмки |
| **Контент** | 50 записей CMS проинвентаризированы, но не допущены автоматически к публикации; судебные исходы и текущие редакции норм требуют первоисточников | Отдельная юридическая и редакционная проверка |

Действующий сайт на старой платформе, текущий DNS и ветка `main` остаются без изменений. Нельзя утверждать, что Vercel, Neon, Auth, Cron, worker, объектное хранилище, продакшен-мониторинг и подтверждённый off-site backup полностью введены в эксплуатацию, пока для этого нет отдельных проверенных результатов.

## 7. Правила текущего офлайн-этапа

- Вносим код и документацию **только** в `feature/dgi-offline-completion` до отдельного решения.
- GitHub Actions разрешены, но **не** вызываем Vercel deploy, не меняем DNS, не подключаем и не изменяем production Neon, не делаем merge в `main`.
- Vercel Git deploy для этой ветки отключён в `vercel.json` и `apps/web/vercel.json`. Не отключать защиту ради проверки документации.
- `SITE_CUTOVER`, `SITE_RELEASE_APPROVED`, `CMS_PUBLIC_READS`, `COURT_DB_READS` не включать в боевой среде до отдельной приёмки.
- Использовать независимые секреты для каждой среды; не загружать токены, личные данные и полные закрытые CMS-экспорты в Git.
- Не подменять юридическую проверку фактом успешной сборки или наличием ссылки на архивный судебный акт.
- Перед запуском обязательно проверить стратегию хранения персональных данных, права на медиа, доступы и восстановление резервных копий.
